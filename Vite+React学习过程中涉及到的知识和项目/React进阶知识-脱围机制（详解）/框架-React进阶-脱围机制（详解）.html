使用ref引用值：

希望组件来记住某些信息，又不希望这些信息触发新的渲染，使用ref

给组件添加ref：

  • 通过从React中导入useRef Hook来为组件添加一个ref：
    • import {useRef} from ‘react’
  • 在组件中调用useRef Hook并传入想要引用的初始值为唯一参数，
    • 例如，这里的ref引用的值时0
      • const ref = useRef（0）；
    • useRef返回一个对象
      • { current: 0 // 你向 useRef 传入的值 }
  • 可以使用ref.current属性访问该ref的当前值，这个值是有意被设置为可变的。就意味着可以读取它也可以更改它。
    • 实例：每次点击按钮会使ref.current递增
      import { useRef } from 'react'; 引入Hook

      export default function Counter() {

      let ref = useRef(0); 定义ref初始值

      function handleClick() {

      ref.current = ref.current + 1; 调用函数会使ref值+1

      alert('你点击了 ' + ref.current + ' 次！'); 提示当前ref值
      }


      return (
      <button onClick={handleClick}>
      点击我！
      </button>
      );
      }
      • 这里的ref指向一个数字，
  • 但是像state一样，可以让他指向任何东西，字符串、对象、函数等。与state不同的是，ref是一个普通的对象，有一个可被读取、修改的current属性
  • 组件不会再每次递增时重新渲染，与state一样，React会在每次重新渲染之后保留ref。但是设置state会重新渲染组件，修改ref不会

ref与state的不同：

  • 多数情况下建议使用state，ref仅是一种脱围机制。
    refstate
    useRef（initialValue）返回{current：initialValue}useState（initialValue）返回state变量的当前值和一个state设置函数（【value，setValue】）
    更改时不会触发重渲染更改时触发重渲染
    可变—在渲染过程之外可以修改和更新current的值不可变—必须使用setState设置函数来修改state变量，从而排队重新渲染
    不应该在渲染期间读取或更改current值可以随时读取state，但是每次渲染都有state快照
    • 实例，使用state实现的计数器
      import { useState } from 'react';

      export default function Counter() {

      const [count, setCount] = useState(0);


      function handleClick() {
      setCount(count + 1);
      }


      return (
      <button onClick={handleClick}>
      你点击了 {count} 次
      </button>
      );
      }
      • 使用setCount（）设置state值，React会重渲染组件，而且屏幕更新显示新的state
    • 实例，使用ref实现相同组件
      import { useRef } from 'react';

      export default function Counter() {
      let countRef = useRef(0);

      function handleClick() {
      // 这样并未重新渲染组件！
      countRef.current = countRef.current + 1;
      }

      return (
      <button onClick={handleClick}>
      你点击了 {countRef.current} 次
      </button>
      );
      }
      • React不会重新渲染组件，计数器不会发生变化，但是实际上的ref.current值被改变了

useRef内部的运行步骤：

  • 尽管useState和useRef都是React提供的Hook，原则上useRef可以在useState的基础上实现。
    • 在React内部，useRef时这样实现
      // React 内部
      function useRef(initialValue) {
      const [ref, unused] = useState({ current: initialValue });
      return ref;
      }
      • 在第一次渲染时，useRef返回{current：initialValue}，该对象由React存储，因此在下一次渲染期间将返回相同的对象。
        • 在这个示例中，setState设置函数没有被使用，而且他是不必要的，因为useRef总是返回相同对象
  • React提供了一个内置版本的useRef，因为他在实践中很常见，但是你可以将其视为没有设置函数的state变量，在面向对象编程中，ref类似于实例字段this.something。但实际结果是somethingRef.current。

何时使用ref：

  • 通常，当你的组件需要跳出React并与外部API通信时，会用到ref，通常不会影响组件外观的浏览器API，下面是常见实例
    • 存储timeout ID
    • 存储和操作DOM元素
    • 存储不需要被用来计算JSX的其他对象。
  • 总结就是，组件需要存储的值，但不影响渲染逻辑，就使用ref存储

ref的实践：

  • 遵守以下ref使用原则，会使组件更具可预测性
    • 将ref视为脱围机制
    • 不要再渲染过程中读取或写入ref.current
  • React state的限制不适用于ref，例如state的快照性质，不会同步更新等。但是更改ref的current值，会立即改变
  • 因为ref本身是普通的JS对象。使用ref时不需要担心避免变更，只要改变的对象不用于渲染，React就不会影响

ref和DOM：

  • 可以将ref指向任何值，最常见的ref用法是访问DOM元素，例如你想以编程方式聚焦一个输入框，使用ref。
    • 将ref传递给JSX中的ref属性时，比如<div ref={myRef}>，React会将响应的DOM元素放入myRef.current中，
    • 当元素从DOM中删除时，React会将myRef.current更新为null。

使用ref操作DOM

由于React会自动处理更新DOM一匹配你的渲染输出，因此组件中通常不需要操作DOM。但是有时需要访问由React管理的DOM元素，例如让一个节点来获得焦点，滚动到它或测量它的尺寸和位置。

在React中没有内置的方法来做这些事情，所以需要指向DOM节点的ref来实现。

获取指向节点的ref

  • 要访问由React管理的DOM节点，首先引入useRef Hook：
    • import {useRef} from ‘react’；
  • 然后，在你的组件中使用它声明一个ref
    • const myRef = useRef（null）
  • 最后将ref作为ref属性值传递给想要获取的DOM节点的JSX标签
    • <div ref={myRef}>
  • useRef Hook返回一个对象，该对象有一个名为current的属性，最初，myRef.current是null，当React为这个div创建一个DOM节点时，React会把对该节点的引用放入myRef.current。然后从事件处理器访问此DOM节点，并使用在上定义的内置浏览器API
    • myRef.current.scrollIntoView（）

示例：使文本输入框获得焦点：

  • 在本例中，单击按钮使输入框获得焦点
    import { useRef } from 'react';

    export default function Form() {

    const inputRef = useRef(null);


    function handleClick() {
    inputRef.current.focus();
    }


    return (
    <>

    <input ref={inputRef} /> 调用后会将该DOM节点赋值给ref
    <button onClick={handleClick}>
    聚焦输入框
    </button>
    </>
    );
    }
    • 实现这一点的流程如下
      • 使用useRef Hook声明inputRef
      • 像<input ref={inputRef}>这样使用ref，就告诉React将这个input的DOM节点放入inputRef.current
      • 在handleClick函数中，从inputRef.current读取input DOM节点并使用inputRef.current.focus（）调用他的focus（）
      • 使用onClick将handleClick事件处理器传递给button
  • 虽然DOM操作是ref最常见的例子，但是useRef Hook可用于存储React之外的其他容器中，例如计时器ID。
  • 与state类似，ref能在渲染之间保留。甚至可以将ref视为设置它们时不会触发重渲染的state变量。

使用ref回调管理ref列表：

  • 上面的例子中，ref的数量是预先确定的，但有时候，你可能需要为列表中每一项都绑定ref，但是又不知道会有多少项，使用列表循环是行不通的
    <ul>
    {items.map((item) => {
    // 行不通！
    const ref = useRef(null);
    return <li ref={ref} />;
    })}
    </ul>
    • 因为Hook只能在组件顶层被调用，不能再循环语句、条件语句、map（）函数中调用useRef
  • 一种可能的解决方案是用一个ref引用父元素，然后使用DOM操作方法，如querySelectorAll来寻找它的子节点，然而这种方法很脆弱，如果DOM结构发生改变，可能会失效或报错
  • 另一种方法是，将函数传递给ref属性，这称为ref回调，当需要设置ref时，React将传入DOM节点来调用ref回调，并在需要清除它时传入null。这可以维护自己的数组或map，并通过索引或某种类型的ID访问任何ref
    • 示例：展示如何使用上述方法滚动到长列表中的任意节点。
      import { useRef, useState } from "react";

      export default function CatFriends() {

      const itemsRef = useRef(null);
      const [catList, setCatList] = useState(setupCatList);


      function scrollToCat(cat) {

      const map = getMap();
      const node = map.get(cat);

      node.scrollIntoView({
      behavior: "smooth",
      block: "nearest",
      inline: "center",
      });
      }

      function getMap() {

      if (!itemsRef.current) {
      // 首次运行时初始化 Map。
      itemsRef.current = new Map();
      }
      return itemsRef.current;

      }

      return (
      <>
      <nav>

      <button onClick={() => scrollToCat(catList[0])}>Neo</button>
      <button onClick={() => scrollToCat(catList[5])}>Millie</button>
      <button onClick={() => scrollToCat(catList[9])}>Bella</button>
      </nav>
      <div>
      <ul>
      {catList.map((cat) => (
      <li
      key={cat}

      ref={(node) => {
      const map = getMap();
      map.set(cat, node);


      return () => {
      map.delete(cat);
      };
      }}
      >
      <img src={cat} />
      </li>
      ))}
      </ul>
      </div>
      </>
      );
      }


      function setupCatList() {
      const catList = [];
      for (let i = 0; i < 10; i++) {
      catList.push("https://loremflickr.com/320/240/cat?lock=" + i);
      }

      return catList;
      }

      • 在这个例子中，itemsRef保存的不是单个DOM节点，而是保存了包含列表项ID和DOM节点的Map（Ref可以保存任何值），每个列表项上的ref回调负责更新Map

        key={cat.id}

        const map = getMap();
        // 添加到 Map 中
        map.set(cat, node);

        return () => {

访问另一个组件的DOM节点：

  • 注意：Ref是一种脱围机制，手动操作其他组件的DOM节点会使代码变得脆弱
  • 可以像其他prop一样将ref从父组件传递给子组件
    import { useRef } from 'react';


    function MyInput({ ref }) {
    return <input ref={ref} />; 这是JSX
    }


    function MyForm() {
    const inputRef = useRef(null);

    return <MyInput ref={inputRef} /> 这是调用MyInput组件传递prop
    }
    • 此处，父组件创建了一个MyFrom的ref，并将它传递给了MyInput子组件，然后MyInput再将这个ref传递给<input>。
    • 因为<input>是一个内置组件，React会将ref的.current属性设置为这个input>DOM元素
  • 再MyFrom中创建的inputRef现在指向MyInput返回的<input>DOM元素，再MyFrom中创建的点击处理程序可以访问inputRef并且调用focus（）来将焦点设置在<input>上。
    import { useRef } from 'react';



    function MyInput({ ref }) {
    return <input ref={ref} />;
    }


    export default function MyForm() {

    const inputRef = useRef(null);



    function handleClick() {
    inputRef.current.focus();
    }


    return (
    <>

    <MyInput ref={inputRef} />
    <button onClick={handleClick}>
    聚焦输入框
    </button>
    </>
    );
    }

使用命令句柄暴露一部分API

  • 上面例子中，MyInput暴露了原始的DOM元素input，这让父元素可以对其调用focus（），然而，这也让父组件能够做其他事情，例如，改变其CSS样式。再不常见情况下，希望限制暴露的功能，可以使用useImperativeHandle来实现
    import { useRef, useImperativeHandle } from "react";


    function MyInput({ ref }) {

    const realInputRef = useRef(null);
    useImperativeHandle(ref, () => ({
    // 只暴露 focus，没有别的
    focus() {
    realInputRef.current.focus();
    },

    }));

    return <input ref={realInputRef} />;
    };


    export default function Form() {

    const inputRef = useRef(null);

    function handleClick() {
    inputRef.current.focus();
    }

    return (
    <>
    <MyInput ref={inputRef} />
    <button onClick={handleClick}>聚焦输入框</button>
    </>
    );
    }
  • 这里的MyInput中的realInputRef保存了实际的inputDOM节点，但是，useImperativeHandle知识React将你自己指定的对象作为父组件的ref值。
  • 所以From组件内的inputRef.current将只有focus方法，在这种情况下，ref句柄不是DOM节点，而是在useImperativeHanle调用中创建的自定义对象。

React何时添加refs：

  • 在React中，每次更新都分为两个阶段
    • 在渲染阶段：React调用组件来确定屏幕上应该显示什么
    • 再提交阶段：React把变更应用于DOM节点上
  • 通常不希望在渲染期间访问refs，这也适用于保存DOM节点的refs，在第一次渲染期间，DOM节点尚未创建，因此，ref.current值为null，在渲染更新的过程中，DOM节点还没有更新，所以读取refs还早
  • React在提交阶段设置ref.current，在更新DOM之前，React将受影响的ref.current的值设置为null，更新DOM之后，React将他们设置到对应的DOM节点
  • 通常，从事件处理器访问refs，如果你想使用ref执行某些操作，但没有特定的事件可以操作，就需要使用effect

使用refs操作DOM的实践

  • refs是一种脱围机制，只在必须跳出React时使用它们，常见实例包括管理焦点、滚动位置、调用React未暴露的浏览器API
  • 如果坚持聚焦和滚动等非破坏性操作，不会遇到问题，但是如果手动修改DOM，就会与React的更改发生冲突。
    • 例子：一条欢迎消息和两个按钮，第一个按钮使用条件渲染和state切换他的显示和隐藏，就像在React中常做的。第二个按钮使用remove（）DOM API将其从React控制之外的DOM中移除
      import { useState, useRef } from 'react';


      export default function Counter() {

      const [show, setShow] = useState(true);
      const ref = useRef(null);


      return (
      <div>
      <button

      onClick={() => {
      setShow(!show);
      }}>
      通过 setState 切换

      </button>
      <button

      onClick={() => {
      ref.current.remove();
      }}>
      从 DOM 中删除

      </button>
      {show && <p ref={ref}>Hello world</p>}
      </div>
      );
      }
      • 再手动删除DOM元素之后，尝试使用setState，在显示会报错，因为更改了DOM，React不知道如何管理
  • 避免更改由React管理的DOM节点，对于React管理的元素进行修改、添加子元素、删除子元素，会导致不一致的视觉结果，或与上述类似的崩溃
  • 但是不意味着，完全不能这样做，可以安全的谨慎的修改React没有理由更新的部分DOM。例如，某些div在JSX中为空，React没有理由去变动其子列表，因此在这里手动增删元素是可以的

有些组件需要与外部系统同步，例如你希望根据React state控制非React组件、建立服务器链接或当组件在页面显示时发送分析日志。

什么是Effect，与事件Event的区别：

  • 在接触Effect之前，需要熟悉React组件中的两种逻辑类型
    • 渲染代码：位于组件的顶层，你在这里处理props和state，对他们进行转换，并返回希望在页面上显示的JSX。渲染代码必须是纯函数，只根据输入内容，计算输出内容，不进行其他处理
    • 事件处理程序：是组件内部的嵌套函数，他们不光进行计算，还会执行操作。事件处理程序可能会更新输入字段，提交HTTP POST请求，或将用户导航到另一个页面，事件处理程序包含由特定用户操作（例如按钮点击或输入）引起的副作用（改变程序的状态）
  • 有时候会使用其他组件，ChatRoom组件，在页面上显示时必须连接到聊天服务器，连接到服务器并不是纯函数（是一个副作用），因此他不能再渲染期间发生，然而，并没有特定的事件（比如点击）能让ChatRoom被显示
  • Effect允许你指定由渲染自身，而不是特定事件引起的副作用
  • 就比如在聊天中发送消息是一个事件，因为他直接由用户点击特定按钮引起。然而建立服务器连接是一个Effect，因为无论哪种交互导致组件出现，他都应该发上升，Effect再提交结束后，页面更新后运行。此时是将React组件与外部系统（如网络或第三方库）同步的最佳时机

可能不需要Effect：

  • 不要急于在组件中使用Effect。
  • Effect通常用于暂时跳出React并于一些外部系统进行同步。包括浏览器API、第三方小组件、以及网络等等。
  • 如果Effect只是根据其他状态来调整状态，那么可能不需要使用Effect

如何编写Effect：

  • 要编写一个Effect，遵循以下三个步骤
    • 声明Effect：通常Effect会在每次提交后运行。
    • 指定Effect依赖：大多数Effect应该按需运行，而不是在每次渲染后都运行，例如，但如动画应该只在组件出现时触发，连接与断开服务器的操作只应在组件中出现消失时，或者切换聊天室时执行。需要通过指定依赖项来学习如何控制这一点。
    • 必要时添加清理操作：一些Effect需要制定如何停止、撤销，或清除他们所执行的操作，例如“连接”需要“断开”，“订阅”需要“退订”，”获取数据“需要“取消”或”忽略“

第一步：声明Effect：

  • 从React中导入useEffect Hook
    • import {useEffect} from ‘react’；
  • 在组件顶部调用，并加入一些代码
    function MyComponent() {
    useEffect(() => {
    // 每次渲染后都会执行此处的代码
    });
    return <div />;
    }
  • 每当组件渲染时，React会先更新页面，然后再运行useEffect中的代码，换句话说，useEffect会延迟一段代码的运行，知道渲染结果反映在页面上。
  • 接下来，演示如何使用Effect与外部系统同步，考虑一个<VideoPlayer>React组件，通关传递一个isPlaying prop来控制它不妨或暂停音频
    • <VideoPlayer isPlaying={isPlaying} />
  • 这个VideoPlayer组件渲染了浏览器内置的video>标签
    function VideoPlayer({ src, isPlaying }) {
    // TODO：使用 isPlaying 做一些事情
    return <video src={src} />;
    }
  • 但是浏览器中video>标签没有isPlaying属性，控制它的唯一方式是在DOM元素中调用play（）和pause（）方法，因此，需要将isPlaying prop的值（表示是否应该播放）与play（）和pause（）等函数的调用进行同步。
    • 首先要获取video>DOM节点的对象引用
    • 然后尝试在渲染期间调用play（）或pause（）
      import { useState, useRef, useEffect } from 'react';

      function VideoPlayer({ src, isPlaying }) {
      const ref = useRef(null);

      if (isPlaying) {
      ref.current.play(); // 渲染期间不能调用 `play()`。
      } else {
      ref.current.pause(); // 同样，调用 `pause()` 也不行。
      }

      return <video ref={ref} src={src} loop playsInline />;
      }

      export default function App() {
      const [isPlaying, setIsPlaying] = useState(false);
      return (
      <>
      <button onClick={() => setIsPlaying(!isPlaying)}>
      {isPlaying ? '暂停' : '播放'}
      </button>
      <VideoPlayer
      isPlaying={isPlaying}
      src="https://interactive-examples.mdn.mozilla.net/media/cc0-videos/flower.mp4"
      />
      </>
      );
      }
    • 这段代码会报错，因为他在渲染期间对DOM节点进行操作。在React中，渲染应该是纯粹的计算JSX，不应该包含任何像修改DOM的副作用
    • 而且第一次调用VideoPlayer组件时，对应的DOM节点还不存在，因为React在返回JSX之前不知道要创建什么样的DOM，所以没有DOM节点可以调用play（）或pause（）方法。
      • 解决办法是使用useEffect包裹副作用，把他分离到渲染逻辑的计算过程之外
        import { useEffect, useRef } from 'react';

        function VideoPlayer({ src, isPlaying }) {
        const ref = useRef(null);


        useEffect(() => {
        if (isPlaying) {
        ref.current.play();
        } else {
        ref.current.pause();
        }
        });


        return <video ref={ref} src={src} loop playsInline />;
        }
      • 将DOM更新封装在Effect中，可以让React先更新页面，在运行Effect。
      • 当VideoPlayer组件渲染时，无论是否为首次渲染，都会发生以下步骤：首先React会更新页面，确保video标签带着正确的props出现在DOM中，之后React将运行Effect，最后Effect根据isPlaying的值调用play（）或pause（）
  • 在上述示例中，同步到React state的外部系统时浏览器媒体API，也可以使用类似的方法将传统的非React代码（如jQuery插件）封装成声明式的React组件
  • 要注意的是，控制视频播放器在实际应用中复杂很多：比如调用play（）会失败，用户可能会使用内置的浏览器控件来进行播放或暂停操作。

  • 默认情况下，Effect会在每次选然后运行，这有时是不想要的
    • 有时，他会运行很慢，与外部系统的同步不是即时的，所以可能希望在不必要时跳过他，例如不想在每次打字时都会重新连接聊天服务器
    • 有时，他会报错，例如，不想再每次按键时都出发组件的但如动画，动画应该只在组件首次出现时播放。
  • 示例：在之前例子中加入console.log调用和一个更新父组件state的文本输入框。注意在输入时是如何触发Effect重新运行的

第三步：按需添加清理（cleanup）函数：

  • 考虑一个不同的例子。加入正在编写一个ChatRoom组件，该组件在显示时需要连接到聊天服务器，现在为你提供了createConnection（）的API，该API返回一个包含connect（）与disconnection（）方法的对象。
    • 如何确保组件在显示时始终保持连接？
      • 首先，编写Effect的逻辑
        useEffect(() => {
        const connection = createConnection();
        connection.connect();
        });
      • 如果每次重新渲染后都得重新连接，会很慢，需要添加依赖数组
        useEffect(() => {
        const connection = createConnection();
        connection.connect();
        }, []);
      • 由于Effect中的代码没有使用props或state，所以依赖数组为空数组，尽在组件首次挂载时运行Effect
        • chat.js
          export function createConnection() {
          // 真正的实现实际上会连接到服务器
          return {
          connect() {
          console.log('✅ 连接中……');
          },
          disconnect() {
          console.log('❌ 连接断开。');
          }
          };
          }
        • App.js
          import { useEffect } from 'react';
          import { createConnection } from './chat.js';

          export default function ChatRoom() {
          useEffect(() => {
          const connection = createConnection();
          connection.connect();
          }, []);
          return <h1>欢迎来到聊天室！</h1>;
          }
      • 这里的Effect仅在组件挂载时运行，但实际上”连接中“被打印了两次
        • 假设ChatRoom组件是一个大型多页面应用中的一部分，用户最初再ChatRoom页面，组件挂载并调用connection.connect（），接着用户可能会导航到另一个页面，比如切换到设置页面，于是ChatRoom组件被卸载。最后，用户点击返回时，ChatRoom组件再次挂载，这将建立第二个连接—但第一个链接未被销毁，随着用户在应用中来回切换，这连接将不断累积。
        • 这类bug在没有大量手动测试的情况下很容易被忽略，在开发环境中，React会在组件首次挂载后立即重新挂载一次。
      • 两次出现“连接中”，出现问题：在代码中，组件被卸载时没有关闭连接。
    • 为解决这个问题，可以在Effect中返回一个清理（cleanup）函数。
      useEffect(() => {
      const connection = createConnection();
      connection.connect();
      return () => {
      connection.disconnect();
      };
      }, []);
  • React会在每次Effect重新运行之前调用清理函数，并在组件卸载之后，在调用一次清理函数
    • 示例，清理函数步骤
      • chat.js
        export function createConnection() {

        return {
        connect() {
        console.log('✅ 连接中……');
        },
        disconnect() {
        console.log('❌ 连接断开。');
        }
        };
        }
      • App.js

  • 在开发环境中，通过重新挂载你的组件，React验证了离开页面在返回后不会导致代码出错。因为本就应该先断开再重新连接。无论是只执行一次Effect，还是执行、清理、在执行，都应该没有用户可见的区别，之所以会有额外的一次connect/disconnect调用，是因为再开发环境下React检测代码中的bug，这是正常现象。
  • 在生产环境下，只会看到“连接中”打印一次。这是因为重新挂载组件只会在开发环境下运行，来帮助找到需要清理的Effect，

如何处理再开发环境下Effect运行了两次：

  • React有意在开发环境下重新挂载你的组件，来找到类似上例中的bug，需要思考的不是“如何只运行一次Effect”，而是“如何修复Effect来让他在重新挂载后正常运行。”
    • 通常是使用清理函数，清理函数应该停止或撤销Effect所做的一切，原则是用户不应该感受到Effect只执行了一次（再生产环境中）和连续执行“挂载-清理-挂载”（开发环境中）之间的区别。
  • 编写的Effect应该符合下列常见模式之一
    • 管理非React小部件
    • 订阅事件
    • 触发动画
    • 获取数据
    • 发送分析报告
  • 不使用Effect的的模式
    • 初始化应用
    • 购买商品

【解释上述模式】

  • 管理非React小部件 ：
    • 有时需要添加不是使用React实现的UI部件，比如在页面中添加一个地图组件，有一个setZoomLevel（）方法，然后希望地图的缩放比例和代码中的zoomLevel state保持同步，你的Effect类似于
      useEffect(() => {
      const map = mapRef.current;
      map.setZoomLevel(zoomLevel);
      }, [zoomLevel]);
      • 这种情况下，不需要清理操作，在开发环境中，R二act会调用Effect两次，但是没关系，使用相同的值调用setZoomLevel两次不会造成任何影响，虽然在开发环境下可能会稍微慢一些，但是问题不大，生产环境下他不会多余的重新挂载
    • 有些API可能不允许连续调用两次，例如内置的<dialog>元素的showModal方法，在连续被调用两次时会爆出一场，此时就可以通过实现清理函数来使其关闭对话框
      useEffect(() => {
      const dialog = dialogRef.current;
      dialog.showModal();
      return () => dialog.close();
      }, []);
      • 开发环境中，Effect会先调用showModal（）然后立即调用close（），之后再次调用showModal（），这与再生产环境中只调用一次showModal（）的用户可见行为是相同的
  • 订阅事件：
    • 如果Effect订阅了某些事件，清理函数应该退订这些事件
      useEffect(() => {
      function handleScroll(e) {
      console.log(window.scrollX, window.scrollY);
      }
      window.addEventListener('scroll', handleScroll);
      return () => window.removeEventListener('scroll', handleScroll);
      }, []);
      • 在开发环境中，你的Effect湖西岸调用addEventListener（），然后立即调用removeEventListener（），接着再次使用享用的处理函数调用addEventListener（），因此每次只会有一个有效订阅，这与再生产环境中只调用一次addEventListener（）所产生的用户可见行为是相同的
  • 触发动画：
    • 如果Effect触发了一些动画，清理函数应该将动画重置为初始状态
      useEffect(() => {
      const node = ref.current;
      node.style.opacity = 1; // 触发动画
      return () => {
      node.style.opacity = 0; // 重置为初始值
      };
      }, []);
      • 开发环境中，透明度由1到0再变为1，这与再生产环境中，直接将其设置为1具有相同的用户可见行为。如果你使用了支持补间动画的第三方动画库，你的清理函数应该将时间轴重置为初始状态。
  • 获取数据：
    • 如果Effect需要获取数据，清理函数硬终止请求或忽略其结果
      useEffect(() => {
      let ignore = false;

      async function startFetching() {
      const json = await fetchTodos(userId);
      if (!ignore) {
      setTodos(json);
      }
      }

      startFetching();

      return () => {
      ignore = true;
      };
      }, [userId]);
      • 无法撤销已经发生的网络请求，但是清理函数应到确保哪些不在相关的请求不会继续影响你的应用。例如userId从alice变为bob，确保alice的响应数据被忽略，即使他在bob之后到达
    • 开发环境中，会在浏览器调试工具中的网络选项卡看到两条请求，使用上述方法，第一个Effect立即被清理，所以他的ignore变量会被设置为true，因此即使有额外的请求，由于if（！ignore）的检查，也不会影响state。
    • 生产环境中，只有一条请求，如果开发环境中的第二次请求造成了困扰，最好的办法是使用一个能够对请求去重并缓存响应的方案
      function TodoList() {
      const todos = useSomeDataLibrary(`/api/user/${userId}/todos`);
      // .
      • 这样可以提高开发体验，还可以是你的应用响应更快，例如用户点击返回按钮时，不用再等待数据重新加载，因为以及缓存好了，可以构建这样的缓存机制，也可以使用很多再Effect中手动获取数据的替代方法。
  • 发送分析报告：
    • 下面代码，再页面访问时发送一个分析事件
      useEffect(() => {
      logVisit(url); // 发送 POST 请求
      }, [url]);
      • 开发环境中，对于每个URL，logVisit会被调用两次，因此你可能会尝试修复，这个东西建议保持不变，与之前示例类似，运行一次还是两次，在用户可见行为上没有区别，从实际角度来看，logVisit不应该在开发环境中执行任何操作，因为不想让开发设备的日志影响生产环境的统计数据。每次保存文件时组件都会重新挂载，因此再开发环境中会记录额外的访问日志。
      • 在生产环境中，不会有重复的访问日志
      • 为了调试发送的分析事件，你可以将应用部署到一个运行在生产模式下的暂存环境，或者暂时禁用 严格模式 及其仅在开发环境中的重新挂载检查。你还可以在路由更改的事件处理程序中发送分析数据，而不是在 Effect 中发送。对于更精确的分析，可以使用交叉观察器 来跟踪哪些组件位于视口中以及它们保持可见的时间。

【解释上述不适合模式】：

  • 初始化应用：

  • 购买商品：
    • 有时，即便编写了清理函数，也无法避免用户观察到Effect运行了两次，比如你的Effect发送了一个像购买商品这样的POST请求

    • 购买操作不是渲染引起的，而是由特定的交互引起的，他应该只在用户按下按钮时执行，因此，他不应该写在Effect中，应当把/api/buy请求移动到购买按钮的事件处理程序中。
      function handleClick() {
      // ✅ 购买行为是一个事件，因为它是由特定的交互引起的。
      fetch('/api/buy', { method: 'POST' });
      }
      • 这说明了，如果重新挂载破坏了应用的逻辑，通常变暴露了存在的bug。对用户而言，访问同一个页面，不应该与访问页面后点击链接、再按下返回按钮查看页面有区别。
      • React通过再开发环境中重新挂载组件来验证你的组件是否遵守这一原则。

可能不需要使用Effect：

Effect时React范式中的一种脱围机制，可以脱离React并使组件和外部的一些系统同步，比如非React组件、网络、浏览器DOM。如果没有涉及到外部系统（例如，像根据props或state的变化来更新一个组件的state），就不应该使用Effect。移除不必要的Effect可以使代码更容易理解，运行得更快

如何移除不必要的Effect：

  • 有两种不必使用Effect的常见情况。
    • 不必使用Effect来转换渲染所需的数据：
      • 例如想在展示一个列表前先做筛选。直觉告诉你可能写一个当列表变化时更新state变量的Effect。然而这是低效的。当更新state时，React会首先调用组件函数来计算，应该显示的内容，然后React会把这些变化提交到DOM来更新屏幕，然后React执行Effect，如果Effect也立即更新了state，就会重新执行这个流程，为了避免不必要的渲染流程，应该在组件顶层转换数据，这些大门会在props或state变化时自动重新执行。
    • 不必使用Effect来处理用户事件：
      • 例如，想在用户购买一个产品时发送一个/api/bug的POST请求并展示一个提示，在购买按钮的点击事件处理函数中，你想知道会发生什么，但是当一个Effect运行时，却不知道用户做了什么，比如点击了哪个按钮。这就是为什么通常在相应的事件处理函数中处理用户事件。
    • 可以使用Effect来和外部系统同步，
      • 例如可以写一个Effect来保持一个jQuery的组件和React state之间的同步，也可以使用Effect来获取数据：例如，你可以同步当前的查询搜索与查询结果，记住，比起直接在组件中写Effect，现代框架提供了更有效地，内置的数据获取机制。

以下是常见的实例：

【根据props或state来更新state】：

  • 假设有一个包含了两个state变量的组件：firstName和lastName。想通过他们联合计算出fullName，此外，每当first和last两个组件变化是，fullName都能更新，
    • 第一直觉是添加一个state变量，fullname，并在Effect中更新它
      function Form() {
      const [firstName, setFirstName] = useState('Taylor');
      const [lastName, setLastName] = useState('Swift');

      // 🔴 避免：多余的 state 和不必要的 Effect
      const [fullName, setFullName] = useState('');
      useEffect(() => {
      setFullName(firstName + ' ' + lastName);
      }, [firstName, lastName]);
      // ...
      }
      • 大可不必复杂，而且这样效率同样不高，现时使用fullName的旧值执行了渲染流程，之后立即使用更新后得知重新渲染一遍
    • 移除state变量和Effect
      function Form() {
      const [firstName, setFirstName] = useState('Taylor');
      const [lastName, setLastName] = useState('Swift');
      // ✅ 非常好：在渲染期间进行计算
      const fullName = firstName + ' ' + lastName;
      // ...
      }
  • 如果一个值可以基于现有的props或state计算的出来，不要把它作为一个state，而是在渲染期间直接计算这个值
    • 这会使代码更快，避免了多余的级联更新，更简洁，以及更少出错。

【缓存昂贵的计算】：

  • 这个组件使用它接收到的props中的filter对另一个prop todos进行筛选，计算得出visibleTodos
    • 直觉可能是将结果存放到state中，在使用Effect更新他
      function TodoList({ todos, filter }) {
      const [newTodo, setNewTodo] = useState('');

      // 🔴 避免：多余的 state 和不必要的 Effect
      const [visibleTodos, setVisibleTodos] = useState([]);
      useEffect(() => {
      setVisibleTodos(getFilteredTodos(todos, filter));
      }, [todos, filter]);

      // ...
      }
      • 就像之前的例子一样，没有必要，也很低效
    • 首先移除state和Effect
      function TodoList({ todos, filter }) {
      const [newTodo, setNewTodo] = useState('');
      // ✅ 如果 getFilteredTodos() 的耗时不长，这样写就可以了。
      const visibleTodos = getFilteredTodos(todos, filter);
      // ...
      }
      • 因为getFilteredTodos（）可能会耗时很长，或者有很多todos，这些情况下，newTodo这样不相关的state变量发生变化时，不想要重新执行getFilterTodos（）
    • 可以使用useMemo Hook缓存，或者说记忆（memoize），这个复杂的计算
      import { useMemo, useState } from 'react';

      function TodoList({ todos, filter }) {
      const [newTodo, setNewTodo] = useState('');

      const visibleTodos = useMemo(() => {
      // ✅ 除非 todos 或 filter 发生变化，否则不会重新执行
      return getFilteredTodos(todos, filter);
      }, [todos, filter]);
      // ...
      或者写成
      const visibleTodos = useMemo(() => getFilteredTodos(todos, filter), [todos, filter]);

      }
  • 这回告诉React，除非todos或filter发生变化，否则不要重新执行传入的函数。
    • React会在初次渲染时记住getFilteredTodos（）的返回值，在下次渲染时，如果没有发生变化，就会使用保存的结果，不一样，再调用函数，并保存结果
  • 传入的useMemo的函数会在渲染期间执行，所以只适用于纯函数场景

如何判断计算是复杂昂贵的：

  • 一般来说只有创建或循环了成千上万对象时才会耗费时间，
    • 可以在控制台输出来测量某一段代码的执行时间，来确认
      console.time('筛选数组');
      const visibleTodos = getFilteredTodos(todos, filter);
      console.timeEnd('筛选数组');
    • 触发要测量的交互，例如在输入框中输入，会在控制台看到类似0.15ms的输出日志，如果总耗时达到了一定量及比如1ms或更多，那么计算结果记忆起来memoize是有意义的。
  • useMemo不会让第一次渲染变快，他只是帮助你跳过不必要的更新。
  • 如果你的设备性能比用户的更好，最好通过人工限制工具来测试性能，比如chrome的CPU节流工具。

【当props变化时重置所有state】：

  • 例如ProfilePage组件接收一个prop：userId。页面上有一个评论输入框，你用了一个state：comment来保存它的值，有一天发现，当你从一个人的个人资料导航到另一个时，comment没有被重置，就很容易把评论发送到不正确的个人哪里。
    • 正常来说，想在userId变化时，清除comment变量：
      export default function ProfilePage({ userId }) {
      const [comment, setComment] = useState('');

      // 🔴 避免：当 prop 变化时，在 Effect 中重置 state
      useEffect(() => {
      setComment('');
      }, [userId]);
      // ...
      }
      • 这是低效的，因为ProfilePage和它的子组件首先会使用旧值渲染，然后再用新值重新计算渲染，这样做很复杂，因为需要在ProfilePage里面所有具有state的组件中都写这样的代码。例如评论区的UI是嵌套的，你想清楚嵌套中的comment state
    • 取而代之的是，可以为每个用户的个人资料组件提供一个明确的键来告诉React他们原则上不同的个人资料组件，
    • 将组件拆分为两份，并从外部的组件传递key属性给内部的组件：
      export default function ProfilePage({ userId }) {
      return (
      <Profile
      userId={userId}
      key={userId}
      />
      );
      }

      function Profile({ userId }) {
      // ✅ 当 key 变化时，该组件内的 comment 或其他 state 会自动被重置
      const [comment, setComment] = useState('');
      // ...
      }
    • 通常，当在相同的位置渲染相同的组件时，React 会保留状态。通过将 userId 作为 key 传递给 Profile 组件，使 React 将具有不同 userId 的两个 Profile 组件视为两个不应共享任何状态的不同组件
    • 每当 key（这里是 userId）变化时，React 将重新创建 DOM，并 重置 Profile 组件和它的所有子组件的 state。现在，当在不同的个人资料之间导航时，comment 区域将自动被清空。
    • 请注意，在这个例子中，只有外部的 ProfilePage 组件被导出并在项目中对其他文件可见。渲染 ProfilePage 的那些组件不用传递 key 给它：它们只需把 userId 作为常规 prop 传入即可。而 ProfilePage 将其作为 key 传递给内部的 Profile 组件是它的实现细节而已。

【当prop变化时调整部分state】：

  • 有时候，当prop变化时，可能只想重置或者调整部分state，而不是所有的state
    • List组件接收一个items列表作为prop，然后使用state变量selection来保持已选中的项，
      • 当items接收到一个不同的数组时，想要把selection重置为null
        function List({ items }) {
        const [isReverse, setIsReverse] = useState(false);
        const [selection, setSelection] = useState(null);

        // 🔴 避免：当 prop 变化时，在 Effect 中调整 state
        useEffect(() => {
        setSelection(null);
        }, [items]);
        // ...
        }
        • 每当items变化，List组件会使用旧的selection值渲染，然后React会更新DOM并执行Effect。最后调用setSelection，会导致List以及子组件重新渲染，重新启动整个流程
      • 从删除Effect开始，使用在渲染期间直接调整state来代替Effect
        function List({ items }) {
        const [isReverse, setIsReverse] = useState(false);
        const [selection, setSelection] = useState(null);

        // 好一些：在渲染期间调整 state
        const [prevItems, setPrevItems] = useState(items);
        if (items !== prevItems) {
        setPrevItems(items);
        setSelection(null);
        }
        // ...
        }
        • 这样存储前序渲染可能难以理解，但是他比Effect中更新state要好，上例中指出，在渲染过程中直接调用setSelection，当他执行到return语句退出后，React会立即重渲染List，此时React还没有渲染List的子组件或更新DOM，这使得List的子组件可以跳过渲染旧的selection
    • 在渲染期间更新组件，React会丢弃已经返回的JSX，并立即重新渲染，为了避免非常缓慢的级联重试，React只允许在渲染期间更新同一组件的状态，如果在渲染期间更新另一组件，会报错，
      • 条件判断items！==prevItems是必要的，可以避免无限循环。可以使用类似方法调整state，副作用（比如变化DOM或设置的延时），都应该留在事件处理函数中或Effect中，来保证组件为纯粹
  • 虽然这种方式比Effect更高效，但是大多数组件不会使用
    • 无论如何做，根据props或其他state都会是数据流更难理解和调试，总是检查是否可以通过添加key来重置所有state，或者在渲染期间计算所需内容，
      • 例如可以存储已选中的itemID而不是存储并重置已经选中的item：
        function List({ items }) {
        const [isReverse, setIsReverse] = useState(false);
        const [selectedId, setSelectedId] = useState(null);
        // ✅ 非常好：在渲染期间计算所需内容
        const selection = items.find(item => item.id === selectedId) ?? null;
        // ...
        }
        • 现在不需要调整state，如果包含已选中ID的项出现在列表中，则仍然保持选中状态，如果没有找到匹配的项，则在渲染期间计算的selection将会是null。行为不同，更好处理组件，因为大多数对items的更改仍可以保持选中状态

【在处理函数中共享逻辑】：

  • 假设有一个产品页面，有两个按钮，购买买和付款，都可以让你购买该产品，当用户将产品添加进购物车时，显示一个通知，再两个按钮的click事件处理函数中都调用showNotification（）感觉有点重复，就想要把逻辑存放在Effect中

      • 假设应用在页面重新加载之前，记住了购物车中的产品，如果把一个产品添加到购物车中并刷新页面，通知将再次出现，并且每次刷新该产品页面，都会出现。
        • 这是因为product.isInCart在页面加载时已经为true，上面的Effect每次都会调用showNotification（）
  • 当不确定某些代码应该放在Effect还是事件处理函数中，先问自己为什么要执行这些代码
  • Effect只用来执行哪些显示给用户时组件需要执行的代码
    • 这个例子中，通知应该在用户按下按钮后出现，而不是页面渲染时出现，删除Effect将共享的逻辑放入一个被两个事件处理程序调用的函数中
      function ProductPage({ product, addToCart }) {
      // ✅ 非常好：事件特定的逻辑在事件处理函数中处理
      function buyProduct() {
      addToCart(product);
      showNotification(`已添加 ${product.name} 进购物车！`);
      }

      function handleBuyClick() {
      buyProduct();
      }

      function handleCheckoutClick() {
      buyProduct();
      navigateTo('/checkout');
      }
      // ...
      }
      • 这样移除了不必要的Effect，也修复了问题

【链式计算】：

  • 有时相连接多个Effect，每个Effect都基于某些state来调整其他的state
    function Game() {
    const [card, setCard] = useState(null);
    const [goldCardCount, setGoldCardCount] = useState(0);
    const [round, setRound] = useState(1);
    const [isGameOver, setIsGameOver] = useState(false);

    // 🔴 避免：链接多个 Effect 仅仅为了相互触发调整 state
    useEffect(() => {
    if (card !== null && card.gold) {
    setGoldCardCount(c => c + 1);
    }
    }, [card]);

    useEffect(() => {
    if (goldCardCount > 3) {
    setRound(r => r + 1)
    setGoldCardCount(0);
    }
    }, [goldCardCount]);

    useEffect(() => {
    if (round > 5) {
    setIsGameOver(true);
    }
    }, [round]);

    useEffect(() => {
    alert('游戏结束！');
    }, [isGameOver]);

    function handlePlaceCard(nextCard) {
    if (isGameOver) {
    throw Error('游戏已经结束了。');
    } else {
    setCard(nextCard);
    }
    }

    // ...
    • 代码中存在两个问题
      • 第一是很低效：链式的每个set调用之间，组件及子组件都不得不重新渲染，上面的例子中最坏的情况是”setCard → 渲染 → setGoldCardCount → 渲染 → setRound → 渲染 → setIsGameOver → 渲染“
      • 第二是，不考虑渲染的效率问题，随着代码扩展，链式调用会复杂出错，例如需要添加一种方法来回溯游戏的历史记录，可以通过更新state变量到之前的值实现，然而将card设置为之前某个值会再次触发Effect链，并更改现有数据，这种代码是僵硬脆弱的
  • 在例子中，更好的做法是，尽可能在渲染期间进行计算，以及在事件处理函数中调整state
    function Game() {
    const [card, setCard] = useState(null);
    const [goldCardCount, setGoldCardCount] = useState(0);
    const [round, setRound] = useState(1);

    // ✅ 尽可能在渲染期间进行计算
    const isGameOver = round > 5;

    function handlePlaceCard(nextCard) {
    if (isGameOver) {
    throw Error('游戏已经结束了。');
    }

    // ✅ 在事件处理函数中计算剩下的所有 state
    setCard(nextCard);
    if (nextCard.gold) {
    if (goldCardCount <= 3) {
    setGoldCardCount(goldCardCount + 1);
    } else {
    setGoldCardCount(0);
    setRound(round + 1);
    if (round === 5) {
    alert('游戏结束！');
    }
    }
    }
    }

    // ...
  • 这会高效很多，此外如果是西安路回溯游戏历史的方法，现在可以将每个state变量设置为之前的任何一个值，二不会触发调整其他值的Effect链，需要多个事件处理函数之间的复用逻辑，可以提取成一个函数，并在这些事件处理函数中调用。
  • 记住，在事件处理函数内部，state的行为类似于快照，即使调用了setState（state + 1），state的变量仍是用户点击按钮时的值，如果需要下一个值计算，使用变量去定义它：const thisstate = state+1
  • 某些情况下，无法在事件处理函数中直接计算出下一个state，例如一个有很多下拉菜单的表单，如果下一个下拉菜单的选项取决于前一个下拉菜单选择的值，这时，Effect链是合法的，因为需要与网络进行同步

【初始化应用】：

  • 有些逻辑只在应用加载时执行一次
    • 可能会想要把他放在顶层组件中的Effect中
      function App() {
      // 🔴 避免：把只需要执行一次的逻辑放在 Effect 中
      useEffect(() => {
      loadDataFromLocalStorage();
      checkAuthToken();
      }, []);
      // ...
      }
      • 结果就是他会在开发环境中执行两次代码，这会导致一些问题，例如，可能会是身份验证token无效，因为该函数不是为调用两次而设计的，一般来说，当组件重新挂载时具有一致性，包括顶层App组件
  • 尽管在实际的生产环境中他可能永远不会被重新挂载，但在所有组件中遵循相同的约束条件可以更容易地移动和复用代码，如果某些逻辑帮你须在每次应用加载时执行一次，而不是在每次组件挂载时执行一次，
    • 可以添加一个顶层变量来记录他是否已经执行过了
      let didInit = false;

      function App() {
      useEffect(() => {
      if (!didInit) {
      didInit = true;
      // ✅ 只在每次应用加载时执行一次
      loadDataFromLocalStorage();
      checkAuthToken();
      }
      }, []);
      // ...
      }
    • 同样可以在模块初始化和应用渲染之前执行它
      if (typeof window !== 'undefined') { // 检测我们是否在浏览器环境
      // ✅ 只在每次应用加载时执行一次
      checkAuthToken();
      loadDataFromLocalStorage();
      }

      function App() {
      // ...
      }
  • 顶层代码会在组件被导入时执行一次，即使他没有被渲染，为了避免再导入任意组件时降低性能或产生意外行为，请不要过度使用这种方法，将应用级别的初始化逻辑保留在App.js这样的根组件模块或你的应用入口中

【通知父组件有关的state变化信息】：

  • 假设正在编写一个内部state isOn的Toggle组件，该state可以是true或false。有几种不同的方式来切换（通过点击或拖动）。
    • 你希望在Toggle的state变化时通知父组件，因此暴露了一个onChange事件并在Effect中调用它
      function Toggle({ onChange }) {
      const [isOn, setIsOn] = useState(false);

      // 🔴 避免：onChange 处理函数执行的时间太晚了
      useEffect(() => {
      onChange(isOn);
      }, [isOn, onChange])

      function handleClick() {
      setIsOn(!isOn);
      }

      function handleDragEnd(e) {
      if (isCloserToRightEdge(e)) {
      setIsOn(true);
      } else {
      setIsOn(false);
      }
      }

      // ...
      }
      • 和之前一样，不太理想，Toggle首先更新他的state，然后React会重渲染屏幕，然后React执行Effect中的代码，调用从父组件传入的onChange函数，现在父组件开始更新他自己的state，开启另一个渲染流程，更好的方式是在单个流程中完成所有操作
    • 删除Effect，并在同一个事件处理函数中更新两个组件的state
      function Toggle({ onChange }) {
      const [isOn, setIsOn] = useState(false);

      function updateToggle(nextIsOn) {
      // ✅ 非常好：在触发它们的事件中执行所有更新
      setIsOn(nextIsOn);
      onChange(nextIsOn);

      updateToggle(!isOn);
      }

      updateToggle(true);
      } else {
      updateToggle(false);
      }
      }

      }
      • 通过这种方式，Toggle组件机器父组件都在事件处理期间更新了各自的state，React会批量处理来自不同组件的更新，所以只会有一个渲染流程
    • 也可以完全移除该state，从父组件中接收uisOn
      // ✅ 也很好：该组件完全由它的父组件控制
      function Toggle({ isOn, onChange }) {
      function handleClick() {
      onChange(!isOn);
      }

      function handleDragEnd(e) {
      if (isCloserToRightEdge(e)) {
      onChange(true);
      } else {
      onChange(false);
      }
      }

      // ...
      }
  • 状态提升，允许父组件通过切换自身的state来完全控制Toggle组件，这意味着父组件会包含更多的逻辑，但整体上需要关心的的状态变少。
  • 每当尝试保持两个不同state变量之间的同步时，使用状态提升试试

  • Child组件获取了一些数据并在Effect中传递给Parent组件

    return <Child onFetched={setData} />;

【订阅外部store】：

  • 有时组件需要订阅React state之外的数据，这些数据可能来自第三方库或者内置浏览器API，
    • 由于这些数据可能在React无法感知的情况下发生变化，需要在组件中手动订阅他们，这经常使用Effect来实现
      function useOnlineStatus() {
      // 不理想：在 Effect 中手动订阅 store
      const [isOnline, setIsOnline] = useState(true);
      useEffect(() => {
      function updateState() {
      setIsOnline(navigator.onLine);
      }

      updateState();

      window.addEventListener('online', updateState);
      window.addEventListener('offline', updateState);
      return () => {
      window.removeEventListener('online', updateState);
      window.removeEventListener('offline', updateState);
      };
      }, []);
      return isOnline;
      }

      function ChatIndicator() {
      const isOnline = useOnlineStatus();
      // ...
      }
      • 这个组件订阅了一个外部的strore数据，浏览器的navigator.onlineAPI。由于这个API在服务端不存在，因此不能用初始的HTML，因此state最初会被设置为true，当浏览器store发生变化时，组件会更新他的state
    • 尽管可以使用Effect来实现功能，但是React为此针对性提供了一个Hook来订阅外部store，删除Effect并将其替换为调用useSyncExternalStore

      window.addEventListener('online', callback);
      window.addEventListener('offline', callback);
      return () => {
      window.removeEventListener('online', callback);
      window.removeEventListener('offline', callback);
      };
      }

      function useOnlineStatus() {
      // ✅ 非常好：用内置的 Hook 订阅外部 store
      return useSyncExternalStore(
      subscribe, // 只要传递的是同一个函数，React 不会重新订阅
      () => navigator.onLine, // 如何在客户端获取值
      () => true // 如何在服务端获取值
      );
      }

      function ChatIndicator() {
      const isOnline = useOnlineStatus();
      // ...
      }
  • 与手动使用Effect将可变数据同步到React state相比，这种方法减少错误。通常可以写一个像上面useOnlineStatus（）这样定义Hook，这样就不需要再各个组件中重复写这些代码。

【获取数据】：

  • 许多应用使用Effect来发起数据获取请求，像这样在Effect中写一个数据获取请求是常见的
    function SearchResults({ query }) {
    const [results, setResults] = useState([]);
    const [page, setPage] = useState(1);

    useEffect(() => {
    // 🔴 避免：没有清除逻辑的获取数据
    fetchResults(query, page).then(json => {
    setResults(json);
    });
    }, [query, page]);

    function handleNextPageClick() {
    setPage(page + 1);
    }
    // ...
    }
  • 不需要把这个数据获取逻辑迁移到一个事件处理函数中，
  • 这可能看起来和之前需要讲逻辑存放到事件处理函数之中相互矛盾。到那时考虑到这不是键入事件，这是在这里获取数据的主要原因，搜索数据框的值经常从URL中预填充，用户可以不关心输入框的情况下导航到后退和前进页面。
    • page和query的来源不重要，只要组件可见，就可以通过当前page和query的值保持results和网络数据的同步，这里就是一个Effect的原因。
      • 然而，上面的代码有一个问题。假设你快速地输入 “hello”。那么 query 会从 “h” 变成 “he”，“hel”，“hell” 最后是 “hello”。这会触发一连串不同的数据获取请求，但无法保证对应的返回顺序。例如，“hell” 的响应可能在 “hello” 的响应 之后 返回。由于它的 setResults() 是在最后被调用的，你将会显示错误的搜索结果。这种情况被称为 “竞态条件”：两个不同的请求 “相互竞争”，并以与你预期不符的顺序返回。
  • 修复这个问题，可以添加一个清理函数来忽略较早返回的结果
    function SearchResults({ query }) {
    const [results, setResults] = useState([]);
    const [page, setPage] = useState(1);
    useEffect(() => {
    let ignore = false;
    fetchResults(query, page).then(json => {
    if (!ignore) {
    setResults(json);
    }
    });
    return () => {
    ignore = true;
    };
    }, [query, page]);

    function handleNextPageClick() {
    setPage(page + 1);
    }
    // ...
    }
  • 这确保了在Effect中通过获取数据时，除了最后一次请求的结果都会被忽略
    • 处理竞态条件并不是实现数据获取的唯一难点。你可能还需要考虑缓存响应结果（使用户点击后退按钮时可以立即看到先前的屏幕内容），如何在服务端获取数据（使服务端初始渲染的 HTML 中包含获取到的内容而不是加载动画），以及如何避免网络瀑布（使子组件不必等待每个父组件的数据获取完毕后才开始获取数据）。
  • 这些问题适用于任何UI库，而不仅仅是React，解决这些问题并不容易，这也是现代框架提供了比在Effect中获取数据更有效的内置数据获取机制的原因
    • 如果不使用框架，但希望从Effect中获取数据更符合人类直觉
      • 如下例，将获取逻辑提取到一个自定义Hook中
        function SearchResults({ query }) {
        const [page, setPage] = useState(1);
        const params = new URLSearchParams({ query, page });
        const results = useData(`/api/search?${params}`);

        function handleNextPageClick() {
        setPage(page + 1);
        }
        // ...
        }

        function useData(url) {
        const [data, setData] = useState(null);
        useEffect(() => {
        let ignore = false;
        fetch(url)
        .then(response => response.json())
        .then(json => {
        if (!ignore) {
        setData(json);
        }
        });
        return () => {
        ignore = true;
        };
        }, [url]);
        return data;
        }
  • 后续可以添加一些错误处理逻辑以及跟踪内容是否处于加载中，也可以编写这样的Hook，也可以使用React生态中已经存在的许多解决方案。
  • 虽然仅使用自定义Hook不如使用框架内置的数据获取机制高效，但将数据获取逻辑移动到自定义Hook中将使后续采用搞笑的数据获取策略更加容易
  • 一般来说，不得不编写Effect时，请留意是否可以将某段功能提取到专门的内置API中或一个更具声明性的自定义Hook中。
    • 例如上面的useData，组件总的原始useEffect调用越少，维护应用就变得更加容易。

响应式Effect的生命周期：

Effect与组件有不同的生命周期。组件可以挂载、更新、卸载，Effect只能做两件事：开始同步某些东西，然后停止同步它。

如果Effect依赖于随时间变化的props和state，这个循环可能发生多次，

React提供了代码检查规则来检查是否正确的指定了Effect的依赖项，这能够使Effect与最新的props和state保持同步。

Effect的生命周期：

  • 每个React组件都经历相同的生命周期：
    • 当组件被添加到屏幕上，他会进行组件的挂载
    • 当组件接收到新的props或state时，通常是作为对交互的响应，他会进行组件的更新。
    • 当组件从屏幕上移除时，他会进行组件的卸载
  • 这是很好的思考组件的方式，但是他不适用于Effect，相反，尝试从组件生命周期中跳脱出来，独立思考组件的方式，但并不适用于Effect
  • Effect描述了如何将外部系统与当前的props和state同步，随着代码的复杂，同步的频率可能会增多减少
    • 实例，Effect将组件连接到聊天服务器
      const serverUrl = 'https://localhost:1234';

      function ChatRoom({ roomId }) {
      useEffect(() => {
      const connection = createConnection(serverUrl, roomId);
      connection.connect();
      return () => {
      connection.disconnect();
      };
      }, [roomId]);
      // ...
      }
    • Effect的主体部分指定了如何开始同步
      // ...

      const connection = createConnection(serverUrl, roomId);
      connection.connect();

      return () => {
      connection.disconnect();
      };
      // ...
    • Effect返回的清理函数指定了如何停止同步
      // ...
      const connection = createConnection(serverUrl, roomId);
      connection.connect();

      return () => {
      connection.disconnect();
      };

      // ...
  • 当组件挂载时React会开始同步，当组件卸载时会停止同步。然而这是不完全正确的
  • 有时在组件保持挂载状态的同时，可能还需要多次开始和停止同步

为什么同步可能需要多次进行：

全局变量或可变值可以作为依赖项吗：

  • 可变值，包括全局变量不是响应式的。
    • 例如，像 location.pathname 这样的可变值不能作为依赖项。它是可变的，因此可以在 React 渲染数据流之外的任何时间发生变化。更改它不会触发组件的重新渲染。因此，即使在依赖项中指定了它，React 也无法知道在其更改时重新同步 Effect。这也违反了 React 的规则，因为在渲染过程中读取可变数据（即在计算依赖项时）会破坏 纯粹的渲染。相反，应该使用 useSyncExternalStore 来读取和订阅外部可变值。
  • 另外，向ref.current或从中读取的值也不能作为依赖项，useRef返回的ref独享本身可以作为依赖项，但是其current属性是有意可变的，它允许跟踪某些值而不出发重新渲染，但由于更改它不会触发重渲染，他不是响应式值。React不会知道在其改变时重新运行Effect。

  • 不能选择依赖项，依赖项必须包括Effect中读取的每个响应式值，代码检查工具会强制执行此规则，有时会导致出现无限循环的问题，或者Effect过于频繁的重新同步，不能通过禁用代码来解决问题，下面是解决方案：
    • 检查Effect是否表示了独立的同步过程
      • 如果Effect没有任何同步操作，可能是不必要的，如果他同时进行了几个独立的同步操作，将其拆分为多个Effect
    • 读取props或state的最新之，又不想对其做出反应并重新同步Effect
      • 可以将Effect拆分为具有反应性的部分（保留在Effect中），和非反应性的部分（提取为名为Effect Event的内容）
    • 避免将对象和函数作为依赖项
      • 如果在渲染过程中创建对象和函数，然后再Effect中读取他们，他们将在每次渲染时都不同，这将导致Effect每次都重新同步。

【检查工具】：

  • 检查工具能力是有限的，他只知道依赖关系是否错误，并不知道每种情况下的最佳解决办法，如果静态代码分析工具建议添加某个依赖关系，但添加该关系会导致循环，这并不意味应该忽略静态代码分析工具。
  • 需要修改Effect内部或外部的代码，使该值不是响应式的，也不需要成为依赖项。

将事件从Effect中分开：

事件处理函数只有再次执行同样的交互时才会重新运行，Effect和事件处理函数不一样，它只有在读取的props或state值和上一次渲染不一样时才会重新同步，有时需要这两种行为的混合体：即一个Effect旨在响应某些值时重新运行，但是在其他之变化时不重新运行。

在事件处理函数和Effect中做选择：

  • 以上述聊天室为例，需求如下
    • 组件自动连接选中的聊天室
    • 点击send按钮，组件在当前聊天界面发送消息
  • 假设实现了这部分代码，但是不确定放在那里，是应该使用事件处理函数还是Effect，每当需要回答问题的时候，思考为什么代码需要运行

事件处理函数只在响应特定的交互操作时运行：

  • 从用户角度出发，发送消息时因为点击l特定的send按钮，如果在任意时间或因为其他原因发送消息，用户会觉得混乱
    • 这就是为什么发送消息应该使用事件处理函数。
      • 事件处理函数时处理特定的交互操作时使用
        function ChatRoom({ roomId }) {
        const [message, setMessage] = useState('');
        // ...
        function handleSendClick() {
        sendMessage(message);
        }
        // ...
        return (
        <>
        <input value={message} onChange={e => setMessage(e.target.value)} />

        );
        }
        • 借助事件处理函数，可以确保sendMessage（message）只在用户点击按钮时运行

每当需要同步，Effect就会运行：

  • 聊天室为例，想要让组件于聊天室保持连接

响应式值和响应式逻辑：

  • 直观上，事件处理函数总是手动触发的，比如点击按钮。Effect是自动触发的，每当需要保持同步的时候他们就会开始运行和重新运行
    • 使用更精确的方式考虑这个问题
      • 组件内部声明的state和props变量称为响应式值。
        • 实例，serverUrl不是响应式值，但roomId和message是，他们参与组件的渲染数据流
          const serverUrl = 'https://localhost:1234';

          function ChatRoom({ roomId }) {
          const [message, setMessage] = useState('');

          // ...
          }
      • 这样的响应式值可以因为重新渲染而变化，例如用户可能会编辑message或者在下拉菜单中选中不同的roomId。
  • 事件处理函数和Effect对于变化的响应是不一样的
    • 事件处理函数内部的逻辑是非响应式的
      • 除非用户又执行了同样的操作，例如点击按钮，否则这段逻辑不会再运行，事件处理函数可以在不影响他们变化的情况下读取响应值。
    • Effect内部的逻辑是响应式的
      • 如果Effect要读取响应式值，就必须将他指定为依赖项，如果接下来的重新渲染导致这个值变化，React就会使用新值重新运行Effect内的逻辑
  • 使用示例来说明差异

【事件处理函数内部的逻辑是非响应式的的】：

  • 看如下代码，是否为响应式
    // ...
    sendMessage(message);
    // ...
    • 从用户角度出发，message的变化并不意味着他们要发送消息，只能表明正在输入。
    • 换句话说，发送消息的逻辑不应该是响应式的，他不应该仅仅因为响应式值变化而再次运行，所以将其归入事件处理函数
      function handleSendClick() {
      sendMessage(message);
      }
      • 事件处理函数都是非响应式的，索引只有用户点击send按钮时运行sendMessage（）

【Effect内部的逻辑是响应式的】：

  • 同样如下代码
    // ...
    const connection = createConnection(serverUrl, roomId);
    connection.connect();
    // ...
    • 从用户角度出发，roomId的变化意味着要链接到不同的房间
    • 换句话说，连接房间的逻辑应该是响应式的，需要这几行代码和响应式值保持同步，并在值不同时再次运行，所以将其归入Effect
      useEffect(() => {
      const connection = createConnection(serverUrl, roomId);
      connection.connect();
      return () => {
      connection.disconnect()
      };
      }, [roomId]);
      • Effect是响应式的，所以createConnection和connection.connect（）会因为roomId每个不同的值而运行，Effect让聊天室连接和当前选中的房间保持了同步

从Effect中提取非响应式的逻辑：

  • 当想要混合使用响应式逻辑和非响应式逻辑时，事情就会复杂
    • 例如：假设想在用户连接到聊天室时展示一个通知，并且通过从props中读取当前theme（dark或light）来展示对应颜色的通知
      function ChatRoom({ roomId, theme }) {
      useEffect(() => {
      const connection = createConnection(serverUrl, roomId);
      connection.on('connected', () => {
      showNotification('Connected!', theme);
      });
      connection.connect();
      // ...
      • 但是theme是一个响应值（他会由于重新渲染而变化），并且Effect读取的每一个响应式值都必须在其依赖项中声明，
    • 现在把theme作为Effect依赖项之一

声明一个Effect Event：

  • 使用useEffectEvent这个特殊的Hook从Effect中提取非响应式逻辑
    import { useEffect, useEffectEvent } from 'react';

    function ChatRoom({ roomId, theme }) {
    const onConnected = useEffectEvent(() => {
    showNotification('Connected!', theme);
    });
    // ...
    • 这里的onConnected被称为Effect Event，他是Effect逻辑的一部分，但是其行为更像事件处理函数，他内部的逻辑不是响应式的，而且以至能看到最新的props和state
  • 在Effect内部调用onConnected Effect Event
    function ChatRoom({ roomId, theme }) {
    const onConnected = useEffectEvent(() => {
    showNotification('Connected!', theme);
    });

    useEffect(() => {
    const connection = createConnection(serverUrl, roomId);
    connection.on('connected', () => {
    onConnected();
    });
    connection.connect();
    return () => connection.disconnect();
    }, [roomId]); // ✅ 声明所有依赖项
    // ...
    • 这个方法解决了问题
  • 注意，使用该方法必须从Effect依赖项中移除onConnected，Effect Event是非响应式的并且必须从依赖中删除
  • 可以将Effect Event堪称和事件处理函数相似的东西，主要区别就是事件处理函数只在响应用户交互时运行，而Effect Event是在Effect中触发。Effect Event让你在Effect响应性和不是响应式的代码连接起来。

使用Effect Event读取最新的props和state：

  • Effect Event可以修复之前许多可能试图抑制依赖项检查工具的地方
    • 例如，有一个记录页面访问的Effect
      function Page() {
      useEffect(() => {
      logVisit();
      }, []);
      // ...
      }
      • 稍后向站点中添加多个路由，现在Page组件接收包含当前路径的url props。把url作为logVisit调用的一部分进行传递，但是依赖项检查工具会提示
        function Page({ url }) {
        useEffect(() => {
        logVisit(url);
        }, []); // 🔴 React Hook useEffect 缺少一个依赖项: 'url'
        // ...
        }
        • 想想代码需要什么，需要为不同的URL记录单独的访问，因为每个URL代表不同的页面，换言之，logVisit调用对于url应该是响应式的，
        • 这就是为什么在此情况下，遵循依赖性检查工具并添加url作为依赖项有意义
          function Page({ url }) {
          useEffect(() => {
          logVisit(url);
          }, [url]); // ✅ 声明所有依赖项
          // ...
          }
    • 现在假设想在每次页面访问中包含购物车中的商品数量
      function Page({ url }) {
      const { items } = useContext(ShoppingCartContext);
      const numberOfItems = items.length;

      useEffect(() => {
      logVisit(url, numberOfItems);
      }, [url]); // 🔴 React Hook useEffect 缺少依赖项: ‘numberOfItems’
      // ...
      }
      • 在Effect内部使用了numberOfItems，所以代码检查工具会让你把他添加到依赖项中，但是你不想要logVisit调用响应numberOfItems，
      • 如果用户把某样东西放入购物车，numberOfItems会变化，这并不意味用户再次访问了这个页面。换句话说在某种意义上，访问页面是一个事件，它发生在某个准确的时刻
        function Page({ url }) {
        const { items } = useContext(ShoppingCartContext);
        const numberOfItems = items.length;

        const onVisit = useEffectEvent(visitedUrl => {
        logVisit(visitedUrl, numberOfItems);
        });

        useEffect(() => {
        onVisit(url);
        }, [url]); // ✅ 声明所有依赖项
        // ...
        }
        • 这里的onVisit是一个Effect Event，里面的代码不是响应式的，这就是为什么可以使用numberOfItems（或者其他响应式值。）而不用担心周围代码因为变化重新执行
        • 另一方面，Effect本身仍然是响应式的，内部的代码使用了url props，所以每次因为不用的url重新渲染后Effect都会重新运行，这回依次调用onVisit这个Effect Event
        • 结果是，因为url的变化去调用logVisit，并且读取的一直是最新的numberOfItems，但是如果numberOfItems自己变化，不会引起任何代码的重新运行。

Effect Event的局限性：

  • Effect Event的局限性在于如何使用
    • 只在Effect内部调用他们
    • 永远不要把他们传递给其他组件或者Hook
  • 例如不要像下例传递Effect Event
    function Timer() {
    const [count, setCount] = useState(0);


    const onTick = useEffectEvent(() => {
    setCount(count + 1);
    });

    useTimer(onTick, 1000); // 🔴 避免: 传递 Effect Event


    return <h1>{count}</h1>
    }

    function useTimer(callback, delay) {
    useEffect(() => {
    const id = setInterval(() => {
    callback();
    }, delay);
    return () => {
    clearInterval(id);
    };
    }, [delay, callback]); // 需要在依赖项中指定 “callback”
    }
  • 取而代之，永远直接在使用他们的Effect旁边声明Effect Event
    function Timer() {
    const [count, setCount] = useState(0);
    useTimer(() => {
    setCount(count + 1);
    }, 1000);
    return <h1>{count}</h1>
    }

    function useTimer(callback, delay) {

    const onTick = useEffectEvent(() => {
    callback();

    });

    useEffect(() => {
    const id = setInterval(() => {

    onTick(); // ✅ 好: 只在 Effect 内部局部调用
    }, delay);
    return () => {
    clearInterval(id);
    };

    }, [delay]); // 不需要指定 “onTick” (Effect Event) 作为依赖项
    }
  • Effect Event是Effect代码的非响应式片段，他们应该在使用它们的Effect旁边。

移除Effect依赖

编写Effect时，linter会验证是否已经将Effect读取的每一个响应式值（props或state）包含在Effect的依赖中，正可以确保Effect与组件的props和state保持同步，不必要的依赖可能会导致Effect运行时过于频繁，甚至产生无限循环。

依赖和代码保持一致：

  • 当编写Effect时，无论这个Effect要做什么，首先要确定它的生命周期，也就是运行流程

当移除一个依赖时，证明他不是一个依赖：

  • 不能选择Effect的依赖。
    • 每个被Effect所使用的响应式值，必须在依赖中声明，依赖是由Effect的代码决定的

  • 移除一个依赖，需要向linter证明Effect不需要这个依赖，

  • Effect的工作流程中有一个模式

    • 然后，采取linter的建议，调整依赖，来匹配所改变的代码
    • 如果对以来不满意，可以回到第一步重新修改代码
  • 最后一步很重要，如果想改变依赖，首先要改变涉及到的代码，可以把依赖看作Effect的代码所依赖的所有响应式值的列表。
    • 不要选择把什么放在这个列表上，该列表描述了代码，要改变依赖，先修改代码
      • 类似于解方程，有一个目标（例如，移除一个依赖），需要找到与该目标相匹配的代码，

【抑制linter对依赖的检查很危险：】

  • 抑制linter会导致非常不直观的bug，难以发现和修复
    • 实例
      import { useState, useEffect } from 'react';

      export default function Timer() {
      const [count, setCount] = useState(0);
      const [increment, setIncrement] = useState(1);

      function onTick() {
      setCount(count + increment);
      }

      useEffect(() => {
      const id = setInterval(onTick, 1000);
      return () => clearInterval(id);
      // eslint-disable-next-line react-hooks/exhaustive-deps
      }, []);

      return (
      <>
      <h1>
      计数器：{count}
      <button onClick={() => setCount(0)}>重置</button>
      </h1>
      <hr />
      <p>
      每秒递增：
      <button disabled={increment === 0} onClick={() => {
      setIncrement(i => i - 1);
      }}>–</button>
      <b>{increment}</b>
      <button onClick={() => {
      setIncrement(i => i + 1);
      }}>+</button>
      </p>
      </>
      );
      }
      • 比方说，你想“只在 mount 时”运行 Effect。你已经知道可以通过设置 空（[]）依赖 来达到这种效果，所以你决定忽略 linter 的检查，强行指定 [] 为依赖
      • 上面的计数器例子，本应该每秒递增，递增量可以通过两个按钮来控制。然而，由于你对 React “撒谎”，说这个 Effect 不依赖于任何东西，React 便一直使用初次渲染时的 onTick 函数。在后续渲染中， count 总是 0 ，increment 总是 1。为什么？因为定时器每秒调用 onTick 函数，实际运行的是 setCount(0 + 1)[1]，所以你总是看到 1。像这样的错误，当它们分散在多个组件中时，就更难解决了。
      • 这里有一个比忽略 linter 更好的解决方案! 那便是将 onTick 添加到依赖中。(为了确保 interval 只设置一次，使 onTick 成为 Effect Event。)
      • 我们建议将依赖性 lint 错误作为一个编译错误来处理。如果你不抑制它，你将永远不会遇到像上面这样的错误。本页面的剩下部分将介绍这个和其他情况的替代方案。

移除非必要的依赖：

  • 每当调整Effect的依赖以适配代码时，注意一下当前的依赖，当这些依赖发生变化时，让Effect重新运行是否有意义，
    • 想在不同条件下重新执行Effect的不同部分
    • 想只读取某个依赖的最新值，而不是对其变化作出反应
    • 依赖可能会因为它的类型是对象或函数而无意间改变的太频繁。

【是否在读取一些状态来计算下一个状态】

  • 每次有新的消息到达时，这个Effect会用新创建的数组更新messages state

    • 让messages成为依赖会带来问题
      • 每当收到一条消息，setMessages会是组件冲洗匈奴安然一个新的messages数组，包括收到的消息，然而由于Effect现在依赖于messages，这也会重新同步Effect，所以每条新消息都会使聊天重新连接
  • 解决问题，不要再Effect里面读取messages，相反将state更新函数传递给setMessages

    const [messages, setMessages] = useState([]);
    useEffect(() => {
    const connection = createConnection();
    connection.connect();
    connection.on('message', (receivedMessage) => {
    setMessages(msgs => [...msgs, receivedMessage]);
    });
    return () => connection.disconnect();
    }, [roomId]); // ✅ 所有依赖已声明
    // ...

【读取一个值而不对其变化作出反应】：

Hook的名称以use开头：

  • React应用是由组件构成，而组件由内置或自定义Hook构成。
    • Hook命名公约
      • React组件名称必须以大写字母开头
        • 比如StatusBar和SaveButton，React组件还需要返回一些React能够显示的内容，比如JSX
      • Hook的名称必须以use开头，然后紧跟一个大写字母
        • 就像内置的useStatus或者自定义的useOnlineStatus一样，Hook可以返回任何值。
  • 这个公约保证你始终能一眼识别出组件并且知道它的 state，Effect 以及其他的 React 特性可能“隐藏”在哪里。例如如果你在组件内部看见 getColor() 函数调用，就可以确定它里面不可能包含 React state，因为它的名称没有以 use 开头。但是像 useOnlineStatus() 这样的函数调用就很可能包含对内部其他 Hook 的调用！

          export class FadeInAnimation {
          constructor(node) {
          this.node = node;
          }
          start(duration) {
          this.duration = duration;
          this.onProgress(0);
          this.startTime = performance.now();
          this.frameId = requestAnimationFrame(() => this.onFrame());
          }
          onFrame() {
          const timePassed = performance.now() - this.startTime;
          const progress = Math.min(timePassed / this.duration, 1);

          if (progress === 1) {

          }

          this.startTime = null;
          this.frameId = null;
          this.duration = 0;
          }
          }
