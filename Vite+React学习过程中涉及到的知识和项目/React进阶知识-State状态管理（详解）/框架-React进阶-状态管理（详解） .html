框架-React进阶-状态管理（详解）

使用State响应输入：

React空值UI的方式是声明式的，不必直接控制UI的各个部分，只需要声明组件可以处于的不同状态，并根据用户的输入在不同状态之间切换。

声明式UI与命令式UI的比较：

  • 设计UI交互时，要思考UI如何根据用户的操作而相应变化。由用户提交答案的表单示例
    • 向表单输入数据时，提交按钮会随之变成可用状态
    • 当你点击提交后，表单和提交按钮都会变成不可用状态，并且加载动画会随之出现
    • 如果网络请求成功，表单会隐藏，同时提交成功的信息会出现
    • 如果网络请求失败，错误信息会出现，表单变为可用状态。
  • 在命令式编程中，以上的过程会直接告诉你如何去实现交互。必须根据要发生的事，写一些明确的命令操作UI。
    • 理解为坐在车里的司机旁边，然后一步一步告诉他司机该去哪里，他并不知道你想去哪，只是跟着命令行动，如果错误指令，他也会错误操作。
    • 类似于必须从加载动画到按钮的命令每个元素，这种告诉计算机如何去更新UI的编程那个方式被称为命令式编程

声明式的考虑UI：

  • 同样对于实现表单为例，使用React来实现
    • 定位组件中不同的视图状态
    • 确定是什么触发了这些state状态的改变
    • 表示内存中的state（需要使用useState）
    • 删除任何不需要的state变量
    • 连接事件处理函数去设置更新state

步骤1：定位组件中不同的视图状态：

  • 首先需要去考虑可视化UI界面中用户可能跟看到的所有不同的状态
    • 无数据：表单中有一个不可用状态的提交按钮，
    • 输入中：表单中有一个可用状态的按钮，
    • 提交中：表单处于不可用状态，加载动画出现，
    • 成功时：显示成功消息，表单取消渲染
    • 错误时：与输入状态类似，报出错误消息
  • 在添加逻辑之前，去模拟不同的状态或创建模拟状态
    • 示例：对于表单可视部分的模拟，这个模拟被一个status的属性控制，这个属性的默认值为empty

步骤2：确定是什么触发了状态的改变：

  • 可以通过触发state的更新来响应两种输入
    • 人为输入：点击按钮、表单输入内容、导航到链接等等
    • 计算机输入：网络请求得到反馈、定时器被处罚、加载完成一张图片等
  • 上述两种情况，必须设置state变量去更新UI，对于正在开发的表单来说，需要改变state来响应不同的输入
    • 改变输入框内的文本（人为）：根据输入框内容是否为控制，进而决定表单的状态从空值状态，切换到输入中或者切换到原状态
    • 点击提交按钮（人为）：将表单的状态切换到提交中的状态
    • 网络请求成功后（计算机）：将表单的状态切换到成功的状态
    • 网络请求失败后（计算机）：将表单的状态切换到失败的状态，与此同时显示错误信息。

步骤3：通过useState表示内存中的state：

  • 接下来需要在内存中通过useState表示组件中的视图状态，诀窍就是“state的每个部分都是出于变化中的，并且需要让变化的部分尽可能的少。”越复杂的程序，越会产生更多bug
  • 先从绝对必须存在的状态开始，例如存储输入的answer以及存储最后一个错误的error
    const [answer, setAnswer] = useState('');
    const [error, setError] = useState(null);
  • 接下来需要状态变量来代表想要显示的那个可视状态，通常有多种方式在内存中表示。如果不能立即想出最好的方案，就添加足够多的state，确保所有可能的状态都在其中
    const [isEmpty, setIsEmpty] = useState(true);
    const [isTyping, setIsTyping] = useState(false);
    const [isSubmitting, setIsSubmitting] = useState(false);
    const [isSuccess, setIsSuccess] = useState(false);
    const [isError, setIsError] = useState(false);
    • 最初想法可能不是最佳的，经过重构state之后会变得更好

步骤4：删除任何不必需要的state变量：

  • 避免state内容中的重复，从而只需要关注那些必要的部分，重构state结构会使组件更具结构，更易理解，减少重复
  • 目的是防止出现在内存中的state不代表任何你希望用户看到的有效UI的情况。比如在展示错误信息的同时禁用输入框，导致用户无法纠正错误。
    • 下例是一些重构时关于state变量的问题
    • 这个state会不会引发矛盾
      • 例如isTyping与isSubmitting的状态不能同时为true。矛盾的产生通常说明了这个state没有足够的约束条件，两个布尔值由四种组合，但是只有三种有效的状态，可以将他们合并到一个status中，这个值必须是typing、submitting、success这三个中一个
    • 相同的信息是否在另一个state变量中存在
      • 例如isEmpty和isTyping不能同时为true，通过他们成为独立的state变量，可能会导致他们不同步并导致bug。可以移除isEmpty而是用message.length===0
    • 是否可以通过另一个state变量的相反值得到相同的信息
      • isError是多余的，因为可以检查error！==null
  • 清理问题，重构state之后，剩下三个必要的state变量
    const [answer, setAnswer] = useState('');
    const [error, setError] = useState(null);
    const [status, setStatus] = useState('typing'); // 'typing', 'submitting', or 'success'
  • 在不破坏功能的前提下，删除掉的状态变量都是不必要的变量。

选择State结构：

构建良好的state可以让组件变得易于修改和调试，而不会经常出错。下面时构建state结构时的建议

构建state的原则：

  • 当编写一个使用state的组件时，需要选择多少变量，以及对应的数据格式。选择次优的state结构也可以，遵循以下建议可以做出更好策略
    • 合并关联的state：如果同时更新多个state变量，考虑将其合并为一个单独的state。
    • 避免互相矛盾的state：当state结构中存在多个相互矛盾或不一致的state，就可能会留下隐患。尽量避免此情况
    • 避免冗余的state：如果能在渲染期间从组件中的props或现有的state变量中计算出一些信息，就不应该将这些信息放入组建的state中。
    • 避免重复的state：当统一数据在多个state变量之间或多个嵌套对象中重复时，很难保持同步，应该尽可能减少重复
    • 避免深度嵌套的state：深度分层的state更新起来不方便，最好以扁平化的方式构建state
      • 这些背后的原则时使state易于更新而不引入错误。从state中删除冗余和重复数据有助于确保所有部分保持同步。
      • 让你的状态尽可能简单，但不要过于简单

合并关联的state：

  • 不确定使用单个state变量还是多个state变量。
    const [position, setPosition] = useState({ x: 0, y: 0 });

    const [x, setX] = useState(0);

    const [y, setY] = useState(0);

    • 下例，移动光标会同时更新红点的两个坐标

避免冗余的state：

  • 如果能在渲染期间从组件的props或其现有的state变量中计算出一些信息，则不应该把这些信息放到该组件的state中。
    • 以下例表单，表单可以运行，但是里面包含冗余的state
      import { useState } from 'react';

      export default function Form() {
      const [firstName, setFirstName] = useState('');
      const [lastName, setLastName] = useState('');
      const [fullName, setFullName] = useState('');

      function handleFirstNameChange(e) {
      setFirstName(e.target.value);
      setFullName(e.target.value + ' ' + lastName);
      }

      function handleLastNameChange(e) {
      setLastName(e.target.value);
      setFullName(firstName + ' ' + e.target.value);
      }

      return (
      <>
      <h2>Let’s check you in</h2>
      <label>
      First name:{' '}
      <input
      value={firstName}
      onChange={handleFirstNameChange}
      />
      </label>
      <label>
      Last name:{' '}
      <input
      value={lastName}
      onChange={handleLastNameChange}
      />
      </label>
      <p>
      Your ticket will be issued to: <b>{fullName}</b>
      </p>
      </>
      );
      }
    • 三个state变量firstname、lastname、fullname，其中fullname是多余的。
  • 在渲染期间可以使用firstName和lastName，计算出fullName
  • const fullName = firstName + ‘’ + lastName。
  • 这里的fullName不是一个state变量，理解为这是渲染期间中计算出的常量。
    • 当setfirstname或者lastname，会重新渲染，并重新计算一个fullname

不要在state中镜像props

  • 下面是体现state冗余的例子
    function Message({ messageColor }) {
    const [color, setColor] = useState(messageColor);
    • 这里的color state变量被初始化为messageColor的prop，这代码问题在于，如果父组件稍后传递不同的messageColor值。例如将blue更改为red。则color state变量将不会更新。state尽在第一次渲染期间初始化。
  • 这就是在state变量中，镜像一些prop属性会导致混淆的原因，相反，在代码中直接使用messageColor属性。就可以使用常量表示
    function Message({ messageColor }) {
    const color = messageColor;
    • 这种写法就不会从父组件传递的属性失去同步。
  • 只有当你想要忽略特定props属性的所有更新时，将props镜像到state才有意义。prop以initial或default开头。来阐明该prop新值会被忽略
    function Message({ initialColor }) {
    // 这个 `color` state 变量用于保存 `initialColor` 的 **初始值**。
    // 对于 `initialColor` 属性的进一步更改将被忽略。
    const [color, setColor] = useState(initialColor);

受控组件与非受控组件

  • 通常把包含“不受控制状态”的组件称为“非受控组件”。例如，最开始带有isActive状态变量的Panel组件就是不受控的，因为父组件无法控制面板的激活状态。
  • 组件的重要信息是由props而不是自身状态驱动。该组件为“受控组件”。这就允许父组件完全指定其行为，最后带有isActive属性的Panel组件就是由Accordion组件控制
  • 非受控组件通常不需要太多配置，但是组合使用，会更复杂。受控组件就具有更大的灵活性，但是他们需要父组件使用props对其进行配置。
  • 受控与非受控并不是严格的技术术语。通常每个组件都同时拥有内部状态和props。这对于如何设计和提供功能的思维是有帮助的。
  • 当编写一个组件时，应该考虑哪些信息受控制（使用prop控制），那些信息不受控制（使用state）。可以随时改变主意并重构代码

每个状态都对应唯一的数据源：

  • 在React应用中，很多组件都有自己的状态，一些状态可能活跃在子组件中，例如输入框。零一些状态可能在应用程序顶部活动，例如客户端路由库是通过将当前路由存储在React状态中，利用props将状态层层传递下去实现。
  • 对于每个独特的状态，都应该存在且只存在于一个指定的组件中作为state
  • 这一原则称为拥有“可信单一数据源”。并不意味所有状态都在一个地方，对每个状态而言，都需要一个特定的组件来保存这些状态信息。
  • 应该将状态提升到公共父级，或将状态传递到需要他的子级中，而不是在组件之间复制共享的状态。

迁移状态逻辑到Reducer中：

对于拥有许多状态更新逻辑的组件来说，过于分散的事件处理程序可能会出错。对于这种情况，可以将组件的所有状态更新逻辑整合到一个外部函数中，这个函数叫做reducer

使用reducer整合状态逻辑：

  • 随着组件的复杂度增加，你将很难一眼看清所有的组件状态更新逻辑

      • 声明action对象为第二个参数
      • 从reducer返回下一个状态，React会将旧状态更新为新状态。

reduce为何被称为reduce：

  • 尽管reducer可以减少组件内的代码量，但实际上十一数组上的reduce（）方法命名的
  • reduce（）允许你将数组中的多个值累加成一个值
    const arr = [1, 2, 3, 4, 5];
    const sum = arr.reduce(
    (result, number) => result + number
    ); // 1 + 2 + 3 + 4 + 5

对比useState和useReducer：

  • 下面从多角度对比二者
    • 代码体积：state适用于少量代码，reducer
    • 可读性：逻辑简单state好，逻辑复杂useReducer好
    • 可调试性：state难发现报错问题，reducer可以观察状态
    • 可测试性：reducer是一个纯函数。便于测试
    • 个人偏好
  • 在修改某些组件状态是经常出现问题或想给组件添加更多逻辑，建议使用reducer。

编写一个好的reducer：

  • 编写reducer牢记两点要求
    • reducer是纯函数：这一点和状态更新函数是相似的，reducer是在渲染时运行的，actions会排队到下一次渲染，意味着reducer必须纯粹，即输入相同，输出也相同。reducer不应包含异步请求、定时器及对任何对组件外部有影响的操作。他们应该以不可变值的方式去更新对象和数组。
    • 每个action都描述了一个单一的用户交互，既便会引发数据多个变化：
      • 举例说明：如果用户在一个由reducer管理的表单（包含五个表单项）中点击了重置按钮，那么dispatch一个reset_form的action比dispatch五个单独的set_field的action更加合理。
      • 如果在一个reducer中打印了所有的action日志，那么这个日志清楚记录了已发生的交互或响应。

个人理解useReducer与reducer：

useReducer是React提供的一个Hook，用于管理组件中的状态。useReducer使用一个reducer函数来定义状态如何更新。

useReducer的基本语法：

  • const 【state，dispatch】=useReducer（reducer，initialState）
    • state：当前的状态。
    • dispatch：用于触发状态更新的函数。
    • reducer：一个纯函数，接收当前状态和动作对象，返回新的状态。
    • initialState：初始状态。

reducer是一个纯函数，作用是根据当前状态和传入的动作对象（action）计算并返回一个新的状态。

  • function reducer（state，action）{
    • //根据action的类型和数据，返回新的状态，一般使用switch或if/else
  • }

action动作对象是一个普通的JS对象，通常包含以下字段

  • type：描述要执行的操作（通常是字符串常量），可以理解为一个名字来链接reducer和dispatch
  • payload（可选），额外参数
  • 执行流程
    • 初始化状态
      • useReducer接收counterReducer和initialState两个参数，并将状态初始化为{count：0}
    • 触发状态更新
      • 每个按钮通过dispatch发送一个动作对象（action），例如（type：‘increment’）
      • dispatch调用后，React会将当前状态和动作对象传递给reducer
    • reducer计算新状态
      • reducer根据action.type决定如歌更新状态，并返回一个新的状态对象。
      • React会用这个新状态重新渲染组件。
    • 重新渲染组件
      • 状态更新后，React会重新调用组件函数，使用最新状态渲染UI

如何使用useReducer（建议使用辅助函数封装）

  • 首先，定义useReducer基本结构
    • const 【state，dispatch】 = useReducer（reducer，initialState）；
      • state：当前状态
      • dispatch（action）：发送一个指令
      • reducer（state，action）：根据action返回新状态
  • 第二，创建initialState和reducer函数
    • 定义初始状态
      • const initialState={count：0}
    • reducer负责根据action类型更新状态
      function reducer(state, action) {
      switch (action.type) {
      case 'increment':
      return { count: state.count + 1 };
      case 'decrement':
      return { count: state.count - 1 };
      case 'reset':
      return { count: 0 };
      default:
      return state;
      }
      }
  • 第三，使用辅助函数封装dispatch
    • 例如在组件中想要使用如下来调用函数，来触发dispatch
      • actions.increment（）；
    • 不是直接使用事件触发dispatch
      • <button onClick={()⇒dispatch({type:’increment’})}>—</button>
    • 使用辅助函数来封装所有操作，也可以使用多个辅助函数独立封装操作
      function createActions(dispatch) {
      return {
      increment: () => dispatch({ type: 'increment' }),
      decrement: () => dispatch({ type: 'decrement' }),
      reset: () => dispatch({ type: 'reset' }),
      };
      }
  • 最后，整理全部useReducer过程
    import React, { useReducer } from 'react';

    // 初始状态
    const initialState = { count: 0 };

    // reducer 函数
    function reducer(state, action) {
    switch (action.type) {
    case 'increment':
    return { count: state.count + 1 };
    case 'decrement':
    return { count: state.count - 1 };
    case 'reset':
    return { count: 0 };
    default:
    return state;
    }
    }

    // 封装的 actions 工厂函数
    function createActions(dispatch) {
    return {
    increment: () => dispatch({ type: 'increment' }),
    decrement: () => dispatch({ type: 'decrement' }),
    reset: () => dispatch({ type: 'reset' }),
    };
    }

    // 组件
    function Counter() {
    const [state, dispatch] = useReducer(reducer, initialState);
    const actions = createActions(dispatch); // 创建封装的动作

    return (
    <div>
    <h2>Count: {state.count}</h2>
    <button onClick={actions.decrement}>-</button>
    <button onClick={actions.increment}>+</button>
    <button onClick={actions.reset}>Reset</button>
    </div>
    );
    }

    export default Counter;

使用Context深层传递参数：

通常来说，使用props将信息从父组件传递给子组件，如果必须通过许多中间组件向下传递props，或者在应用中许多组件传递相同的信息，传递props会变得冗长和不变。

Context允许父组件向下层无论多深的任何组件提供信息，而无需通过props显示传递

传递props带来的问题：

  • 传递props是将数据通过UI树显示传递到使用它的组件的方法。
  • 但是当需要在组件树中深层传递参数，以及需要在组件间复用相同的参数时，传递props会变得很麻烦，
  • 最近的根节点父组件可能里需要数据的组件很远，状态提升太高的层级，会导致逐层传递props的情况
    • prop逐级透传
  • React的context功能可以实现在组件树中不需要props将数据直接传输到需要的组件。

在使用context之前需注意：

  • 使用Context看起来很简单，这也就意味着他容易被过度使用，如果只是想把一些props传递到多个层级中，并不意味着需要把这些信息放到context中。
  • 使用context之前，考虑以下替代方案
    • 传递props。如果组件看起来不起眼，那么通过十几个组件向下传递一堆props很常见。这些会让组件使用了哪些数据清晰明了。这样使用props会让数据流变得清晰
    • 抽象组件并将JSX作为children传递给它们。如果你通过很多层不使用该数据的中间组件来传递数据，意味着在此过程中忘记了抽象组件。
      • 例如传递一些像posts的数据props倒不会直接使用这个参数的组件，类似<layout posts={posts} />。取而代之，让layout把children作为一个参数，然后渲染<layout><Posts posts={posts} /></layout>。这样就减少了定义数据的组件和使用数据的组件之间的层级。
    • 如果这两种方法都不合适，在考虑使用context

Context的使用场景：

  • 主题：如果应用允许用户更改其外观（例如俺也模式），可以在应用顶层放一个context provider，并在需要调整其外观的组件中使用该context。
  • 当前账户：许多组件可能需要知道当前登录的用户信息。将它放到context中可以方便的在书中的任何位置读取她，某些应用还允许你同时操作多个用户（例如，以不同的用户的身份发表评论），在这种情况下，将UI的一部分包裹到具有不同账户数据的provider中会很方便
  • 路由：大多数路由解决方案在其内部使用context来保存当前路由。这就是每个连接直到她是否处于活动状态的方式，如果你创建自己的路由库。
  • 状态管理：随着你的应用增长，最终靠近应用顶部的位置可能会有很多state，许多遥远下层组件可能想要修改它，通常将reducer与context搭配来使用管理复杂的状态并将其传递给深层的组件来避免过多的麻烦
    • Context不局限于静态之。如果在下一次渲染时传递不同的值，React会更新读取他的所有下层组件。这就是context经常和state结合使用的原因。

使用Reducer和Context拓展应用

Reducer可以整合组件的状态来更新逻辑。Context可以将信息深入传递给其他组件。可以组合使用他们共同管理一个复杂页面的状态。
